## 1 核心结论

二期建议沿用一期路线图的 V0.2 范围，以 **文件资料库、统一标签、全局关键词搜索** 为主线。用户应能把资料放进工作空间或项目，关联到任务和笔记，再通过内容、标签和项目快速找回，并继续原来的工作。

产品采用当前知识管理工具常见的上下文附件、统一搜索、可组合筛选和清晰处理状态。技术延续现有模块化单体，优先使用 PostgreSQL 完成检索，不因二期增加独立搜索集群。借鉴依据和适用边界见[业界方案调研](v0.2-research.md)。

存储方案已按用户现有环境确定为 RustFS，二期增加 AWS SDK for Java 2.x 的统一 S3 API 封装，复用已运行容器。推荐按 11 周组织实施，假设配置 1 名后端、1 名前端和 0.5 名测试。27 项 P0 的基准工作量为 53.5 人日，另留 10.7 人日风险储备；后端依赖决定日历工期。这属于规划估算，开工验证后调整。单人兼任全部角色时，建议约 19 周，详见[实施计划](v0.2-delivery-plan.md)。

## 4 用户价值与核心场景

### 4.1 项目资料归集

用户在项目中上传需求 PDF 或方案 DOCX，系统自动继承项目范围，展示上传和处理进度。用户给文件添加“需求”“参考”等标签，再将同一文件关联到项目任务或笔记，无须重复上传。

### 4.2 找回信息后继续工作

用户记得“缓存方案”这一内容，但忘了写在笔记还是附件里。在顶部搜索后，结果同时呈现项目、任务、笔记和文件；用户按类型或项目缩小范围，查看命中摘要，打开来源，返回时仍保留筛选和页码。

### 4.3 组织零散资料

暂未归属项目的文件保存在工作空间资料库。“未分类”表示没有项目且没有标签。用户可以逐个整理，按标签查看不同类型的内容；批量整理作为后续增强。

### 4.4 处理失败仍能继续

文本提取失败不等同于上传失败。原文件可用时，用户仍能下载，通过文件名查找，并看到失败原因与是否可重试。扫描型 PDF 或图片明确提示“暂不支持正文搜索”，避免把未命中误认为资料丢失。

## 5 范围与优先级

P0 为 V0.2 正式交付条件；P1 为 V0.2.x 增强，未纳入基准工作量；P2 为后续版本。

| 模块 | P0 必须交付 | P1 后续增强 |
| --- | --- | --- |
| 文件资料库 | 上传、列表、详情、下载、安全预览、重命名、项目归属、软删除和文件回收站 | 批量标签、批量归类、更大文件和断点续传 |
| 上下文附件 | 项目文件分区；任务和笔记附件区；引用已有同范围文件 | 粘贴图片、正文内嵌附件、跨项目引用 |
| 内容处理 | PDF、DOCX、TXT、MD 文本提取；状态、失败原因、限次重试 | OCR、PPTX/XLSX/CSV 结构化提取 |
| 统一标签 | 四类对象共用标签；创建、重命名、颜色、解绑、删除；标签筛选 | 合并标签、批量操作、嵌套标签 |
| 全局搜索 | 四类对象，中文与英文关键词，摘要、筛选、排序、分页、来源跳转 | 保存搜索、最近访问、模糊纠错和更精细排序 |
| 可靠性 | 工作空间隔离、幂等、配额、异步重试、删除同步、索引重建、关键指标 | 专用任务平台与运营后台 |
| S3 存储封装 | RustFS 私有桶；统一写/读/HEAD/删除/受控枚举/探针接口；校验、错误和资源管理 | CopyObject、预签名、分片上传和更多部署提供方 |

以下不属于本期：AI 对话、自动总结、Embedding、语义搜索、RAG、Agent、MCP 接入、外部云盘同步、公开分享、多人邀请、复杂权限、通用回收站、文件版本历史和在线 Office 编辑。

二期为 AI 保留稳定的来源 ID、内容版本、文本提取状态和索引重建入口。无需为了“AI 就绪”提前建立向量库、对话记录或无人执行的自动化系统。

## 6 关键产品决策

1. **统一入口，保留上下文。** 主导航增加“文件”，全局搜索放在顶部；标签位于筛选和设置，不增加独立一级导航。
2. **资料可复用，归属可解释。** 文件属于一个 Workspace，可选归属一个 Project；任务、笔记附件只能引用同项目范围的文件，包括同为无项目的情况。
3. **区分原文件与提取结果。** 上传成功即可看到文件；正文须处理成功后才可检索，状态分别记录。
4. **标签是数据，不是临时字符串。** 独立标签 ID，跨对象统一引用；正文中的 `#文字` 不自动成为标签。
5. **搜索结果来自全部授权数据。** 页面上已加载多少条，不影响全局结果；检索前后都必须保持 Workspace 和生命周期边界。
6. **中文短词单独验证。** 两字中文是正式验收场景，不能假设英文全文搜索配置天然满足中文需求。
7. **减少基础设施。** 先采用数据库索引、持久化任务和存储接口。独立搜索服务只在容量与检索质量证明需要时再引入。

## 7 成功指标

下列数字是二期验收目标，不是当前实测结果。样本、环境和计算口径见[测试计划](../development/v0.2-quality-release.md)。

| 指标 | 建议目标 |
| --- | --- |
| 核心用户闭环 | 上传 → 添加标签 → 关联笔记/任务 → 搜索正文 → 返回来源，端到端全部通过 |
| 数据隔离与删除 | 所有隔离负例零泄漏；删除提交后，新请求不得返回结果、摘要、计数或文件内容 |
| 搜索耗时 | 参考环境 5 万条索引文档、10 并发，普通检索 P95 ≤ 800ms |
| 搜索可用性 | 60 条人工标注查询中，至少 90% 在前 5 条结果找到指定目标 |
| 索引新鲜度 | 普通业务对象变更提交至可搜 P95 ≤ 5 秒 |
| 文件正文可搜 | ≤ 5MiB 标准文本型文档，接收完成至正文可搜 P95 ≤ 60 秒 |
| 解析成功率 | 支持且未加密、未损坏的固定样本中 ≥ 95%，不把图片无文本算失败 |
| 交互完整性 | 上传、失败、空状态、只读、冲突、返回上下文均有可验证操作 |

## 8 评审与变更原则

存储提供方已确定为 RustFS，开工前确认实际人员、应用连接方式、镜像摘要及桶/凭据权限。第一周启动中文检索和文件解析验证，第二周初据结果冻结 P0 范围，随后完成实际 RustFS 与 SDK 兼容验证。任何新增能力必须说明用户价值、依赖、增加的人日以及替换哪项工作。

若工期收紧，先整体延后 P1，再分阶段开放 P0。缺少隔离、删除一致性、可恢复处理或核心验收时，不将局部预览称为二期已完成。
