# V0.2 业界方案调研与选型依据

调研日期：2026-09-18  
用途：为二期产品设计和技术决策提供可核查依据

[二期总览](v0.2-plan.md) · [技术架构](../architecture/v0.2-architecture.md)

## 1 调研结论

对于当前以个人使用为主、已有项目任务笔记底座的应用，适合吸收成熟工具的三种做法：内容在工作上下文中收集；标签与筛选帮助组织；搜索结果直接回到来源。文件处理、授权和可恢复索引是实现这些体验的基础。

本调研采用产品官方帮助和技术官方文档，不把案例数量等同于市场占有率，也不据此宣称某个方案最流行。下文“事实”描述来源已说明的能力，“采用建议”是结合本项目规模作出的判断。未开展生产基准测试，性能和工作量仍需在二期开工验证。

## 2 产品体验参考

| 参考 | 官方材料支持的事实 | 本项目采用建议 | 暂不跟进 |
| --- | --- | --- | --- |
| Notion 搜索 | 工作空间搜索与数据库局部搜索范围不同；支持内容检索和若干筛选、排序条件 | 顶部全局搜索与页面局部筛选明确区分；结果附来源和摘要 | 不照搬其团队空间与企业搜索管理 |
| Obsidian 附件 | 可拖入或粘贴附件，在笔记中引用，并配置附件存放位置 | 保留文件实体，让笔记引用文件；上传时继承当前项目上下文 | 正文内嵌、文件系统同步放后续 |
| Obsidian 标签 | 标签可点击并用于检索；其标签不区分大小写，支持层级 | 标签选择器、点击筛选和统一大小写规则 | 不直接照搬正文语法或嵌套标签 |

来源：[Notion Search](https://www.notion.com/help/search)、[Obsidian Attachments](https://github.com/obsidianmd/obsidian-help/blob/master/en/Editing%20and%20formatting/Attachments.md)、[Obsidian Tags](https://github.com/obsidianmd/obsidian-help/blob/master/en/Editing%20and%20formatting/Tags.md)。

本项目的具体推导是：保持一期减少入口的方向，将“文件”作为唯一新增主导航；全局搜索承担跨对象查找；标签承担跨项目分类。无需新建包含相同内容的“知识库首页”。

## 3 检索路线比较

| 方案 | 当前适配度 | 主要收益 | 主要代价或边界 | 二期决策 |
| --- | --- | --- | --- | --- |
| 业务表逐一模糊查询 | 适合小规模验证 | 最少新增结构 | 跨对象排序、正文提取和扩展困难 | 保留既有局部查询，不作为全局长期结构 |
| PostgreSQL 检索投影和 GIN | 高 | 复用现有服务，授权与对象状态可同库校验 | 需要自行定义中文短词策略和重建流程 | 作为 P0 默认方案 |
| 独立关键词搜索服务 | 在更大规模或更复杂相关性需求时评估 | 可独立扩展检索能力 | 多一套部署、索引同步、备份和权限一致性 | 不作为 P0 依赖 |
| 向量检索与混合检索 | 面向后续语义问答 | 支持语义相关性能力 | 增加模型、向量、评测和成本管理 | 按原路线留给 V0.4 |

PostgreSQL `pg_trgm` 支持相似度以及 `LIKE`、`ILIKE` 等索引检索，但官方明确指出，没有可提取 trigram 的模式可能退化为全索引扫描。不能据此承诺两字中文和所有短查询都高效。[PostgreSQL 16 pg_trgm](https://www.postgresql.org/docs/16/pgtrgm.html)

PostgreSQL 原生 GIN 支持数组包含操作，可用来存储并过滤应用生成的二元字符组。将短词候选过滤与最终字面子串匹配结合，是本项目的设计选择，不是 PostgreSQL 官方提供的完整中文搜索方案。[GIN 内建操作类](https://www.postgresql.org/docs/16/gin-builtin-opclasses.html)

本期建议采用规范化文本、二元字符组候选召回和字面复核，先验证正确性、短词召回及索引体积。`pg_trgm` 作为可选性能优化；不在首版同时叠加分词、向量与多套排序。技术细节见[检索设计](../architecture/v0.2-architecture.md#5-关键词检索设计)。

如果后续启用语言分词，PostgreSQL 官方文档将 GIN 列为全文检索的优先索引类型；但选择 GIN 本身不解决中文分词和相关性评估。[全文检索索引](https://www.postgresql.org/docs/16/textsearch-indexes.html)

## 4 文件处理路线

OWASP 建议上传功能采用类型白名单、大小限制、服务端验证、应用生成存储名称、独立存储位置和权限检查。本项目据此将“原始名称”与“存储键”分离，限制格式，并让每次内容访问经过服务端授权。[File Upload Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)

Apache Tika 官方说明，直接在应用进程解析不可信文件可能消耗同一进程的 CPU 与内存，进程隔离及资源限制由调用方负责；服务端接口也不能直接作为面向不可信用户的安全边界。因此，本项目建议选用 Tika 作为解析适配器，但部署在受限的独立进程或内网容器，禁止公网调用和任意外部抓取。[Apache Tika Security](https://tika.apache.org/docs/4.0.x/security.html)

Tika 文档页面的版本分支用于核实设计原则，不视为本项目已选定依赖版本。开工时按 Java 25、解析格式和公开安全公告验证维护中的稳定版本，并固定制品版本与校验值。[Apache Tika 安全公告](https://tika.apache.org/security.html)

## 5 上传与存储方案

S3 预签名 URL 可在有效期内重复使用，同一对象键的上传可能覆盖原对象。因此，“拿到上传链接”并不等于一次性上传完成或对象不可变。[S3 预签名 URL](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

用户已提供运行中的 RustFS，二期据此确定存储提供方。RustFS 官方推荐使用 AWS S3 SDK；项目采用 AWS SDK for Java 2.x，再封装为 ObjectStorage，业务通过已鉴权的文件 API 使用。[RustFS SDK 概览](https://docs.rustfs.com/en/developer/sdk)

考虑到二期单文件上限为 20MiB，采用后端流式接收到受限临时文件、生成独立尝试对象键、写入 RustFS 后核对大小和摘要。临时目录不承担永久存储，开发和后续部署均用 RustFS 私有桶。大文件、直传、分片和断点续传在 P1 单独设计；已运行实例仍须对具体镜像与 SDK 组合执行兼容验收，详见 [S3 封装](../architecture/v0.2-s3-storage.md)。

文件下载也先经后端授权代理，避免软删除后旧下载地址仍在有效期内可用。后续引入预签名下载时，必须重新定义撤销时效及对象版本语义。

## 6 后台任务与一致性

业务变更与待处理事件在同一个数据库事务提交，再由后台消费者处理，是本项目保证任务可恢复的设计。采用至少一次处理语义，要求消费者幂等，不能写成“消息只执行一次”。

PostgreSQL 官方说明 `SKIP LOCKED` 可用于队列式表的多个消费者避免行锁竞争，但不适合需要完整一致视图的一般查询。因此仅在后台领取任务时使用，不用于用户搜索或权限判断。[PostgreSQL SELECT 锁定说明](https://www.postgresql.org/docs/16/sql-select.html)

## 7 后续升级触发条件

- 连续两次在目标容量压测中，数据库索引优化后仍无法达到检索延迟目标，再评估专用搜索服务。
- 用户需要同义表达、跨语言查找或基于资料回答问题时，启动独立的语义检索评测，不以关键词命中率替代问答质量。
- 文件规模或网络条件使 20MiB 限额和后端代理成为可观测瓶颈时，再增加直传和断点续传。
- 部署从个人可信使用扩展到开放注册、多租户或公开文件接收前，增加恶意文件扫描、滥用控制和相应运维容量，单独评审。

以上触发条件是演进决策依据，不属于二期范围的隐含扩张。
